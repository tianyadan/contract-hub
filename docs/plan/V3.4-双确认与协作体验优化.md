> 修复「单方确认即锁定」、分享链接未门禁、在线状态抖动与展示不显眼等问题，提升内外部协作可信度与可感知性。

## 1. 背景与目标

### 1.1 问题清单

| # | 问题 | 影响 |
|---|------|------|
| A | 分享链接打开即可看到合同内容 | 客户身份未校验，协作审计链不完整 |
| B | WebSocket 在线状态频繁掉线/误判 | 协作者无法信任「谁在线」 |
| C | 在线用户展示在页面右上角 | 两人协作时存在感弱，易忽略 |
| D | 一方点击「确认合同」即锁定全文 | 违背「双方合意」业务规则；另一方无法继续编辑 |
| E | 缺少统一设计文档 | 后续迭代难以对齐行为 |

### 1.2 目标

| 目标 | 验收标准 |
|------|----------|
| 分享姓名门禁 | 打开分享链接仅见权限/有效期；输入姓名 `join` 成功后才加载合同正文 |
| 双方确认锁定 | 存在外部协作者时，须 **内部（type=0）+ 外部（type=1）** 均确认当前版本后，最后一次确认才生成终稿 PDF 并 `status=3` |
| 在线状态精准 | 服务端每 **1 秒** 向房间广播全量 `presence` 列表；前端断线指数退避重连 |
| 在线展示显眼 | 编辑区 **上方** 独立 `OnlinePresenceBar`，展示头像、姓名、内外部角色与在线人数 |
| 文档沉淀 | 本文档记录 API、状态机与前后端改动清单 |

### 1.3 与 V3.3 的关系

V3.3 将「确认」与「终稿 PDF 归档」绑定，但默认 **单方确认即完成**。V3.4 在保留 PDF 管线的前提下，将确认拆为 **两阶段**：

```text
第一次确认（任一方）→ 仅写入 contract_confirmation，合同仍可编辑
第二次确认（另一方）→ 必须携带终稿 PDF → FinalizeConfirmWithPdfArchive → 锁定
```

无外部协作者的纯内部合同：**行为与 V3.3 一致**（单方确认 + PDF 即锁定）。

## 2. 用户流程

### 2.1 外部分享链接（姓名门禁）

```text
打开 /share/{token}
    → GET /api/share/{token}  仅返回 permission / expire_time（无合同名称、无正文）
    → 展示「进入合同协作」门禁卡片，要求输入姓名
    → POST /api/share/{token}/join { name }
    → sessionStorage 写入 lshc_share_name_{token}
    → 加载合同内容、变更、版本、确认记录；建立 WebSocket（需已有姓名）
```

**安全说明**：`GET /api/share/{token}/contract` 等数据接口仍要求 `collaborator_name`；未 join 的姓名无法通过校验。

### 2.2 双方确认（有外部协作者）

```text
内部用户点击「确认合同」
    → GET confirm-progress：requires_dual_confirm=true, will_finalize_on_next=false
    → POST confirm（无 PDF）→ status=pending，提示「等待外部协作者确认」
    → 合同 status 仍为可编辑（1/2）

外部协作者点击「确认合同」
    → GET confirm-progress：will_finalize_on_next=true
    → 浏览器生成终稿 PDF（二维码）→ POST confirm（multipart 含 PDF）
    → status=completed，合同 status=3（已确认锁定）

（顺序可颠倒：外部先确认、内部后确认，逻辑对称）
```

### 2.3 单方确认（无外部协作者）

```text
合同从未产生外部 collaborator 记录
    → requires_dual_confirm=false
    → 内部一次确认即走完整 PDF 归档流程（与 V3.3 相同）
```

### 2.4 在线协作感知

```text
用户进入详情页 / 分享页（已 join）
    → WebSocket 连接对应合同房间
    → 服务端每 1s 广播 { type: "presence", list: [...] }
    → 编辑区上方 OnlinePresenceBar 实时展示在线名单
    → 断线后 2s 起指数退避重连（上限 15s），连接中显示「连接中…」
```

## 3. 双方确认状态机

### 3.1 判定条件

| 字段 | 含义 |
|------|------|
| `requires_dual_confirm` | `contract_collaborator` 表中该合同是否存在外部协作者 |
| `has_internal_confirm` | 当前版本是否存在 `confirmer_type=0` 且 `confirm_status=1` 的记录 |
| `has_external_confirm` | 当前版本是否存在 `confirmer_type=1` 且 `confirm_status=1` 的记录 |
| `will_finalize_on_next` | 本次操作方确认后是否满足双方，从而需要 PDF |

### 3.2 ProcessConfirmation 核心逻辑

实现文件：`backend/internal/service/contract_confirm.go`

```text
1. 合同已 status=3/4 → ErrAlreadyConfirmed
2. 当前用户/协作者已确认该版本 → ErrAlreadyConfirmedByUser
3. requires_dual=false → 直接 FinalizeConfirmWithPdfArchive（须 PDF）
4. requires_dual=true 且 willComplete=false → CreateConfirmation only → { status: "pending" }
5. requires_dual=true 且 willComplete=true → 须 input.PdfData → FinalizeConfirmWithPdfArchive → { status: "completed" }
```

### 3.3 前端确认分支

工具：`frontend/src/utils/confirmProgress.ts`

- `willFinalizeAfterConfirm(progress, myType)`：内部用户看 `has_external_confirm`；外部用户看 `has_internal_confirm`
- `needPdf === false` → 调用 `confirmContractAck` / `confirmShareAck`（无文件）
- `needPdf === true` → `prepareFinalExport` → 生成 PDF → `confirmContractWithPdf` / `confirmShareWithPdf`

## 4. API 变更

### 4.1 新增

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/contracts/{id}/confirm-progress` | 内部用户查询双方确认进度 |
| GET | `/api/share/{token}/confirm-progress?collaborator_name=` | 外部协作者查询进度 |

**响应体 `ConfirmProgress`：**

```json
{
  "requires_dual_confirm": true,
  "has_internal_confirm": false,
  "has_external_confirm": true,
  "pending_parties": ["内部用户（合同发起方）"],
  "will_finalize_on_next": true
}
```

### 4.2 修改

| 方法 | 路径 | 变更 |
|------|------|------|
| GET | `/api/share/{token}` | 返回 `SharePublicVO`：仅 `permission`、`permission_text`、`expire_time`；**不含**合同名称与正文 |
| POST | `/api/contracts/{id}/confirm` | 响应 `ConfirmOutcome`；PDF **可选**（首位确认方可不传） |
| POST | `/api/share/{token}/confirm` | 同上 |

**`ConfirmOutcome`：**

```json
{
  "status": "pending",
  "message": "您已确认当前版本，等待对方确认后可生成终稿并锁定合同",
  "pending_parties": ["外部协作者"]
}
```

或

```json
{
  "status": "completed",
  "message": "双方已确认，终稿 PDF 已归档，合同已锁定"
}
```

### 4.3 新增错误码（HTTP 400）

| 错误 | 说明 |
|------|------|
| `ErrAlreadyConfirmedByUser` | 重复确认同一版本 |
| `ErrPdfRequiredForFinalize` | 双方已齐但请求未带 PDF |

## 5. WebSocket 在线状态

### 5.1 服务端

文件：`backend/internal/ws/hub.go`

| 改动 | 说明 |
|------|------|
| `startPresenceSync(1 * time.Second)` | 定时向每个房间广播全量在线列表 |
| 消息格式 | `{ "type": "presence", "list": [{ "name", "role" }] }` |
| Ping 间隔 | 15s（保持连接存活） |

**设计理由**：仅依赖 join/leave 事件易因网络抖动、页面刷新、消息丢失导致列表不一致；**全量同步**以服务端连接表为唯一真相源。

### 5.2 前端

文件：`frontend/src/hooks/usePresence.ts`

| 改动 | 说明 |
|------|------|
| 仅处理 `type === 'presence'` | 不再本地伪造在线状态 |
| 断线不清空名单后立即标离线用户 | `onclose` 设 `isConnected=false` 并重连 |
| 指数退避 | 2s → 最大 15s |
| 分享页 | 须 `sessionStorage['lshc_share_name_{token}']` 存在才建连 |

连接地址：

- 内部：`/api/ws/contracts/{id}?token=`
- 外部：`/api/share/{token}/ws?collaborator_name=`
