## 1. 背景与问题

### 1.1 现状

| 场景 | 当前实现 | 问题 |
|------|----------|------|
| 模板池 `/templates/:id` | 默认 Tab「高保真预览」= `docx-preview` 渲染 **原始 DOCX**；另一 Tab「结构化编辑」= `DocumentEditor` | 两套渲染引擎，排版/分页/字体与导出 PDF **不一致**；进入页面自动拉取 DOCX 预览，浪费带宽 |
| 合同详情 `/contracts/:id` | 主视图已是 `DocumentEditor`；DOCX 预览折叠在「导入原文件参考」 | 折叠区仍可能被误认为「高保真」，与终稿导出无关 |
| 导出 / 确认 | 浏览器 `preparePagesForExport` → PNG → PDF → OSS | **这才是用户眼中的真实效果**，但未用于「阅览」场景 |
| 版本管理 | 合同有 `contract_version` + 右侧「历史版本」列表（仅查看 JSON） | 无高保真快照版本；无回退；模板仅有 `current_version_no`，无历史 API |

### 1.2 根因

```text
DOCX（docx-preview）  ≠  网页画布（DocumentEditor）  ≠  导出 PDF（html-to-image + jsPDF）
         ↑ 模板池默认展示                    ↑ 编辑真相源              ↑ 法定交付物
```

V3 架构已明确 **「网页即真相」**，高保真阅览必须 **复用导出管线**，而非 DOCX 二次渲染。

### 1.3 一句话目标

> **编辑区维护内容 → 用户手动「生成高保真阅览」→ 与导出相同的截图拼 PDF → 上传 OSS → 网页内嵌预览；每份合同/模板最多保留 5 份高保真快照，支持一键回退到快照对应的文档内容。**

## 3. 方案设计

### 3.1 高保真阅览生成管线（浏览器）

与 V3.3 导出共用前端工具，差异仅在于 **水印与上传类型**：

```text
DocumentEditor.preparePagesForExport()
    → exportPagesAsPng({ draft: true, pixelRatio: 1.5 })
    → exportPagesAsPdf(pngBlobs)          // 不叠加验真二维码
    → sha256Blob(pdfBlob)
    → POST .../fidelity-snapshots         // multipart: file, hash, page_count, source_version_no
    → 返回 snapshot_id + pdf_signed_url
    → 前端 PDF Viewer 展示
```

| 对比项 | 草稿导出 / 高保真阅览 | 终稿确认 |
|--------|----------------------|----------|
| 二维码 | 无 | 每页验真二维码 |
| OSS 路径 | `.../previews/{snapshotId}.pdf` | `.../v{d}/final.pdf` |
| 触发 | 用户手动 | 双方确认最后一击 |
| 下载 | 本期禁用 | 允许 |

### 3.2 双轨版本模型

为避免与现有「保存版本」无限增长冲突，引入 **高保真快照（Fidelity Snapshot）** 实体，与 **内容版本（Content Version）** 解耦：

```text
┌─────────────────────────────────────────────────────────────┐
│  内容版本（现有 contract_version / template_version）          │
│  · 每次「保存」产生，记录 document_content JSON               │
│  · 用于 diff、历史查看、协作编辑                              │
│  · 数量：不硬性限制（或沿用现有分页列表）                      │
└─────────────────────────────────────────────────────────────┘
                              │
                              │ 生成高保真阅览时绑定 source_version_no
                              ▼
┌─────────────────────────────────────────────────────────────┐
│  高保真快照（新增 fidelity_snapshot 表）                      │
│  · 每次手动「生成高保真阅览」产生 1 条                        │
│  · 存储：preview_pdf OSS + hash + page_count                  │
│  · 冗余存储：生成时刻 document_content 快照（用于回退）         │
│  · 数量上限：每份合同 / 每份模板 最多 5 条（FIFO 淘汰）       │
└─────────────────────────────────────────────────────────────┘
```

**「原件与 PDF 的高保真最多保留五个版本」解读：**

| 轨道 | 含义 | 上限 |
|------|------|------|
| 原件快照 | 生成阅览时冻结的 `document_content` JSON | 随快照记录保存，**每合同/模板最多 5 条快照记录** |
| PDF 高保真 | 对应快照的预览 PDF 文件（OSS） | 同上，与原件快照 **1:1 绑定** |

即：**5 条 fidelity_snapshot = 5 组（JSON 原件快照 + 预览 PDF）**，不是内容版本与 PDF 各 5 条。

### 3.3 一键回退语义

```text
用户在某条快照点击「回退到此版本」
    → 二次确认弹窗
    → 读取该快照的 document_content_snapshot
    → 调用 SaveVersion / SaveTemplateContent（change_summary = "回退至高保真快照 #3"）
    → 生成新的内容版本 V(n+1)，current 指针指向新版本
    → 编辑器刷新为新内容
    → 不自动删除或修改历史快照列表
```

**约束：**

- 合同 `status = 3/4`（已确认/作废）时禁止回退
- 回退不产生新的高保真快照（须用户再次手动生成）

### 3.4 模板池页面布局（目标 UX）

```text
┌──────────────────────────────────────────────────────────────┐
│  ← 返回    模板名称 · V3                    [保存模板]         │
├──────────────────────────────────────────────────────────────┤
│  ┌─────────────────────────────┐  ┌────────────────────────┐ │
│  │  DocumentEditor（默认主视图） │  │  版本管理               │ │
│  │                             │  │  [生成高保真阅览]        │ │
│  │                             │  │  ─────────────────────  │ │
│  │                             │  │  快照 #3  09-02 14:30   │ │
│  │                             │  │    [预览] [回退]        │ │
│  │                             │  │  快照 #2  ...           │ │
│  └─────────────────────────────┘  └────────────────────────┘ │
│  修改说明输入框                                               │
└──────────────────────────────────────────────────────────────┘

点击「生成高保真阅览」→ 全屏/抽屉内 PDF Viewer 展示最新生成结果
```

- **移除** Tabs（高保真预览 / 结构化编辑）
- **移除** 进入页面时的 `fetchTemplatePreview` 请求

将现有分散的「版本记录」「历史版本」与新增「高保真快照」整合：

```text
┌─ 版本管理 ─────────────────────────┐
│  [生成高保真阅览]                     │
│                                      │
│  ▼ 高保真快照（最多 5 条）            │
│    #3 · V5 · 6页 · 张三 · 09-02      │

│    #2 · V4 · ...                     │
│                                      │
```

## 4. 数据模型

### 4.1 新增表 `fidelity_snapshot`

```sql
CREATE TABLE fidelity_snapshot (
  id                  BIGINT PRIMARY KEY,
  entity_type         TINYINT NOT NULL COMMENT '0=contract 1=template',
  entity_id           BIGINT NOT NULL COMMENT 'contract_id 或 template_id',
  snapshot_no         INT NOT NULL COMMENT '实体内的快照序号，从 1 递增',
  source_version_no   INT NOT NULL COMMENT '生成时绑定的内容版本号',
  document_content    LONGTEXT NOT NULL COMMENT '生成时刻 JSON 快照，供回退',
  preview_pdf_oss_key VARCHAR(500) NOT NULL,
  preview_pdf_hash    VARCHAR(64) NOT NULL,
  preview_pdf_page_count INT NOT NULL DEFAULT 0,
  created_by_user_id  BIGINT DEFAULT NULL COMMENT '内部用户；模板/合同所有者',
  created_by_name     VARCHAR(64) NOT NULL COMMENT '展示用操作人姓名',
  create_time         DATETIME NOT NULL,
  UNIQUE KEY uk_entity_snapshot (entity_type, entity_id, snapshot_no),
  KEY idx_entity_time (entity_type, entity_id, create_time)
) COMMENT='高保真阅览快照（预览 PDF + 文档 JSON）';
```

**OSS 路径约定：**

| 实体 | Key 模式 |
|------|----------|
| 合同 | `contracts/{contractId}/fidelity/{snapshotId}.pdf` |
| 模板 | `templates/{templateId}/fidelity/{snapshotId}.pdf` |

### 4.2 FIFO 淘汰策略

生成第 6 条快照时：

1. 查询该 `entity_type + entity_id` 下最旧一条
2. `oss.DeleteObject(preview_pdf_oss_key)`
3. `DELETE FROM fidelity_snapshot WHERE id = ?`
4. 插入新记录，`snapshot_no` 可使用自增序号或 `MAX+1`

### 4.3 与现有 `contract_version.export_pdf_*` 的关系

| 字段 | 用途 |
|------|------|
| `contract_version.export_pdf_*` + `verify_code` | **终稿确认**归档，带验真，永久保留（确认后） |
| `fidelity_snapshot.preview_pdf_*` | **阅览预览**，草稿 PDF，最多 5 条，可淘汰 |

二者 **不可混用**。

## 5. API 设计

### 5.1 合同

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/contracts/{id}/fidelity-snapshots` | 列表（≤5 条，按时间倒序） |
| POST | `/api/contracts/{id}/fidelity-snapshots` | 上传预览 PDF + 元数据（multipart） |
| GET | `/api/contracts/{id}/fidelity-snapshots/{snapshotId}` | 详情 + PDF 签名 URL |
| POST | `/api/contracts/{id}/fidelity-snapshots/{snapshotId}/rollback` | 回退：写入新版本 JSON |

**POST body（multipart）：**

| 字段 | 必填 | 说明 |
|------|------|------|
| `file` | 是 | 预览 PDF |
| `hash` | 是 | SHA256 |
| `page_count` | 是 | 页数 |
| `source_version_no` | 是 | 生成时内容版本号 |
| `document_content` | 是 | 生成时刻 JSON 字符串（服务端校验与当前版本一致性或接受客户端快照） |

**响应示例：**

```json
{
  "snapshot_id": 1788179346494020,
  "snapshot_no": 3,
  "pdf_url": "https://oss.../signed",
  "page_count": 6,
  "create_time": "2026-09-02T14:30:00+08:00"
}
```

### 5.2 模板

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/templates/{id}/fidelity-snapshots` | 列表 |
| POST | `/api/templates/{id}/fidelity-snapshots` | 上传预览 PDF |
| GET | `/api/templates/{id}/fidelity-snapshots/{snapshotId}` | 详情 + 签名 URL |
| POST | `/api/templates/{id}/fidelity-snapshots/{snapshotId}/rollback` | 回退并 `SaveContent` 新版本 |

### 5.3 废弃 / 降级

| 接口 | 处理 |
|------|------|
| `GET /api/templates/:id/preview` | **保留**但模板详情页默认不再调用；仅「导入原文件参考」类场景可选使用 |
| `GET /api/contracts/:id/preview` | 同上，维持折叠懒加载 |

## 8. 用户流程

### 8.1 模板维护 + 高保真阅览

```text
上传 DOCX → 进入 /templates/:id（直接看到 Editor）
    → 编辑模板内容 → 保存模板（V2）
    → 点击「生成高保真阅览」
    → 浏览器按导出管线生成 PDF → 上传 OSS
    → 右侧快照列表 +1；弹层/抽屉内展示 PDF
    → 用户核对排版与导出一致
    → 若需回退：点某快照「回退」→ 内容恢复并产生 V3
```

### 8.2 合同协作 + 版本管理

```text
合同详情编辑 → 保存版本
    → 需要给客户看「与终稿一致的预览」时，手动「生成高保真阅览」
    → 右侧版本管理查看快照历史
    → 确认前可多次生成（最多保留 5 次）
    → 双方确认后走 V3.3 终稿 PDF（与阅览快照无关）
```

## 11. 风险与决策记录

| 议题 | 决策 | 理由 |
|------|------|------|
| 为何不用 docx-preview | 废弃作为主路径 | 与导出不一致，违背 V3「网页即真相」 |
| 为何手动生成 | 截图+拼 PDF 耗 CPU/内存 | 用户明确「节省资源」 |
| 快照是否等于内容版本 | 否，解耦 | 保存频繁、阅览按需；5 条上限仅约束快照 |
| 本期是否支持下载阅览 PDF | 否 | 用户明确「暂时不支持下载」 |
| `document_content` 由谁提供 | 客户端随 POST 上传，服务端落库 | 与生成时刻完全一致；可校验 `source_version_no` |
